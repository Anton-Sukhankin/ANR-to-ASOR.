# Компонент: Дерево вложений и статусы обработки

Область: компонент самостоятельного `ai-completeness-module`. Основной дровер использует только выбранные ресурсы пакета и имеет [собственный контракт интеграции](../../../../docs/07-check-workspace-target.md). Этот документ нужен при изменении компонента или его реально используемых данных/стилей, а не как обязательный контекст любой задачи. Примеры данных демонстрационные; браузерные функции `window.*` не являются серверным API.


## 1. Назначение компонента

Компонент `FileTree` отображает структуру вложений загруженного пакета документов и показывает пользователю состояние обработки каждого файла.

Дерево используется во вкладке `ИИ-Анализ комплектности` и связано с правой панелью метаданных. При выборе файла справа открывается карточка документа, интерфейс технических параметров пайплайна или другой сменный режим правой области.

## 2. Основные файлы

```text
src/components/FileTree/
├── FileTree.js
├── FileTree.css
├── file_tree_and_pipelines.md
└── mockTreeData.json
```

## 3. Правило контейнерности и вложенности

Дочерние элементы в дереве разрешены только у реальных файлов-контейнеров.

Контейнерные форматы:

* `.msg`
* `.zip`
* `.7z`
* `.tar`
* `.rar`

Обычные конечные файлы всегда являются листовыми узлами и не получают кнопку раскрытия:

* `.pdf`
* `.doc`
* `.docx`
* `.xls`
* `.xlsx`
* `.jpg`
* `.jpeg`
* `.png`
* `.txt`

Если в исходных mock-данных у обычного файла ошибочно присутствуют `children`, такие дочерние элементы поднимаются на ближайший допустимый уровень. Это сохраняет сами документы в интерфейсе, но убирает ложную иерархию вида `Excel -> PDF` или `PDF -> JPG`.

## 4. Атрибутивный состав узла дерева

Каждый узел дерева должен иметь стабильный набор данных:

```json
{
  "id": "node_1_2",
  "name": "Приложение №1_РСС.xlsx",
  "type": "xlsx",
  "size": 2420000,
  "pipeline_status": {
    "unpack": "green",
    "read": "yellow",
    "check": "red"
  },
  "ai_metadata": {
    "detected_type": "Смета РСС / Спецификация",
    "confidence": 91,
    "error_message": "Описание найденной проблемы"
  },
  "metadata_details": {},
  "filter_metadata": {}
}
```

Обязательные смысловые группы данных:

* `id` — уникальный идентификатор узла.
* `name` — имя файла или контейнера.
* `type` — технический формат файла без точки.
* `size` — размер файла в байтах.
* `pipeline_status` — технические статусы этапов обработки.
* `ai_metadata` — результат AI-классификации и сообщения об ошибках.
* `metadata_details` — данные для правой панели метаданных и технических параметров.
* `filter_metadata` — нормализованные атрибуты для поиска и фильтрации.

## 5. Статусы обработки

В данных сохраняются три технических этапа:

* `unpack` — распаковка.
* `read` — чтение ИИ.
* `check` — комплектность.

Возможные значения:

* `green` — успешно.
* `loading` — выполняется.
* `yellow` — требует проверки.
* `red` — ошибка.
* `gray` — в очереди.

Техническая детализация этапов показывается в правой панели метаданных выбранного файла и в интерфейсе технических параметров пайплайна.

## 6. Пользовательская индикация в строках дерева

В списке файлов не выводятся отдельные аббревиатуры этапов `Р / Ч / К` и отдельные цветовые ячейки этапов.

В строке отображается агрегированная пользовательская индикация состояния:

* форматная подложка с аббревиатурой типа файла;
* цвет подложки и текста зависит от агрегированного статуса;
* точка на подложке используется только для проблемных или незавершенных состояний;
* успешные файлы получают спокойную светло-зеленую подложку без дополнительной точки;
* проблемные строки дополнительно могут иметь левую боковую индикацию, чтобы пользователь быстрее находил элементы, требующие внимания.

## 7. Агрегированный статус строки

Агрегированный статус вычисляется из `pipeline_status` и состояния дочерних элементов контейнера.

Правила приоритета:

1. Если любой этап имеет `red`, строка получает статус ошибки.
2. Если нет `red`, но есть `yellow`, строка требует проверки.
3. Если есть `loading`, строка находится в обработке.
4. Если все этапы `green`, строка считается выполненной.
5. Если этапы ожидают запуска, строка получает статус очереди.

Для контейнеров учитывается состояние дочерних элементов, чтобы проблема внутри архива или письма была видна на уровне родительского контейнера.

## 8. Фильтрация

Фильтрация выполняется по `filter_metadata`, а не по DOM.

Пользовательские группы фильтров:

1. По статусу обработки.
2. По смысловому типу документа.
3. По автору загрузки / ФИО.
4. По техническому формату файла.

Фильтр по отдельным техническим этапам пайплайна не отображается. Для конечного пользователя достаточно агрегированного `filter_metadata.status.overall`; подробность по этапам остается в карточке выбранного файла.

## 9. Контракт `filter_metadata`

```json
{
  "filter_metadata": {
    "status": {
      "overall": "red | yellow | loading | gray | green"
    },
    "pipeline": {
      "stages": [
        { "key": "unpack", "status": "green" },
        { "key": "read", "status": "yellow" },
        { "key": "check", "status": "red" }
      ]
    },
    "semantic_type": {
      "key": "rss_estimate",
      "label": "РСС (сметы)"
    },
    "uploaded_by": {
      "full_name": "Смирнов Кирилл Андреевич",
      "short_name": "Смирнов К.А.",
      "filter_key": "смирнов кирилл андреевич"
    },
    "technical_format": {
      "extension": "xlsx",
      "category": "final_document",
      "is_container": false,
      "is_final_document": true,
      "is_readable_document": true
    },
    "tree_context": {
      "parent_id": "node_1",
      "ancestor_ids": ["node_1"],
      "has_children": false,
      "path_label": "RE_ACOP.msg / Приложение №1_РСС.xlsx"
    },
    "filter_flags": {
      "include_for_status_filter": true,
      "include_for_semantic_filter": true,
      "include_for_uploader_filter": true,
      "include_for_format_filter": true,
      "expand_ancestors_on_match": true
    }
  }
}
```

`pipeline.stages` сохраняется в данных для метаданных и технической детализации, но не используется как отдельная пользовательская группа фильтров.

## 10. Поиск

Поиск работает совместно с фильтрацией.

Поисковая строка сопоставляется с:

* именем файла;
* техническим форматом;
* смысловым типом;
* исходным типом;
* автором загрузки.

Если найден дочерний файл, дерево автоматически раскрывает родительские контейнеры, чтобы пользователь видел путь к найденному документу.

## 11. Общий статус РВЕ и сводная статистика

Верхняя аналитическая зона расположена вне внутреннего блока дерева: между сегмент-контролами вкладки и рабочей областью с двумя панелями.

Зона является единым блоком `rve-dashboard-card` и состоит из двух уровней:

* карточка общего статуса РВЕ;
* набор карточек сводной статистики по структуре вложений.

Верхний уровень является самостоятельным статусным блоком с title, description и иконкой статуса. Вся область верхнего статусного блока работает как зона клика для сворачивания/разворачивания сводной статистики. В обычном состоянии видна статусная метафора, а при hover на верхний статусный блок или focus на саму подложку появляется стрелка раскрытия или сворачивания. Наведение на нижний блок сводной статистики не меняет иконку статуса и не является зоной переключения. Когда нижний уровень раскрыт, верхний уровень отделяется от него сплошным нижним border на всю ширину карточки.

Нижний уровень является строкой сводной статистики. По умолчанию он свернут, чтобы верхняя аналитическая зона не увеличивала высоту интерфейса. После клика по подложке статуса нижний уровень раскрывается плавно через изменение высоты и прозрачности, а стрелка меняется с направления вниз на направление вверх. Каждая ячейка статистики отделяется от соседней правым border, который занимает всю высоту нижнего блока. Последняя ячейка правый border не получает.

### 11.1. Общий статус РВЕ

Карточка общего статуса отображается над сводной статистикой и объясняет итог проверки человеческим языком. Она агрегирует состояние всего пакета документов, а не отдельной строки дерева.

Карточка содержит:

* иконку статуса на цветной подложке;
* динамический title;
* динамический description.

Верхний статусный блок является основной click-зоной переключения. Подложка иконки статуса содержит кнопку `#rve-summary-toggle` с `aria-expanded` и сохраняет доступный клавиатурный сценарий управления блоком `#rve-summary-cards`. Стрелка вниз означает возможность раскрыть сводную статистику, стрелка вверх означает возможность свернуть ее обратно.

Поддерживаются четыре агрегированных состояния:

| Состояние | Title | Description |
| --- | --- | --- |
| `Allowed` / `Done` | `Комплектность подтверждена` | `Все обязательные требования закрыты распознанными документами. РВЕ можно пропускать дальше по процессу.` |
| `Processing` | `Выполняется проверка комплектности` | `Документ проходит стадии распаковки, чтения и проверки комплектности. Пожалуйста, подождите завершения процесса.` |
| `Manual Review` | `Требуется ручная проверка` | `Система распознала документы, но некоторые позиции требуют ручного подтверждения сметчиком.` |
| `Blocked` | `Комплектность не подтверждена` | `Обнаружены критические ошибки или отсутствуют обязательные документы. Дальнейшая обработка невозможна без вмешательства.` |

В прототипе общий статус рассчитывается из текущего mock-дерева:

* красные ошибки пайплайна или отсутствующие обязательные требования дают статус `Blocked`;
* выполняющиеся или ожидающие этапы дают статус `Processing`, если критических ошибок нет;
* предупреждения дают статус `Manual Review`, если критических ошибок нет;
* отсутствие ошибок, предупреждений и ожидания дает статус `Allowed` / `Done`.

Локальный расчёт является демонстрационным. Серверный формат агрегированного результата и его приоритет над локальным расчётом ещё нужно согласовать; этот документ не устанавливает будущий API.

Карточка общего статуса не содержит операционных кнопок. Переход к проблемам и пересчет проверки остаются в блоке `Структура вложений`, где пользователь видит конкретные позиции, алерт комплектности и контекст обработки файлов.

### 11.2. Сводная статистика

Сводная статистика по структуре вложений отображается внутри того же блока, что и общий статус РВЕ. Контракт группировки: семь компактных ячеек с правыми вертикальными разделителями внутри единой панели.

Карточки показывают:

* `Требования` — количество закрытых требований и количество отсутствующих обязательных требований в формате `закрыто/отсутствует`;
* `Комплектность` — процент закрытия проверки с прогресс-линией;
* `Документы` — количество документов;
* `В обработке` — количество документов, которые еще ожидают завершения анализа;
* `Предупреждения` — количество некритичных замечаний;
* `Ошибки` — количество критических ошибок;
* `Профиль проверки` — профиль правил, по которому выполнена проверка, например `АСОР / ПИР v3`.

Значения рассчитываются из текущего дерева при каждой перерисовке. Для требований используется дедупликация по названию требования из `metadata_details.compliance` и `metadata_details.crossLinks`.

## 12. Связь с правой панелью

При клике по строке дерева:

* выбранный узел сохраняется в `window.activeTreeNodeId`;
* правая панель получает данные выбранного документа;
* повторный клик по активной строке снимает выбор и возвращает пустое состояние;
* если открыт интерфейс технических параметров пайплайна, переключение между файлами обновляет технические данные без возврата к обычным метаданным.

## 13. Действия строки

Меню строки содержит действия конкретного документа:

* `Скачать документ`.
* `Пересчитать статус`.

Пересчет статуса запускается только для выбранной позиции. Если позиция является контейнером, пересчет применяется к ней и ее дочерним элементам. Если позиция является дочерним файлом, родительские сущности не пересчитываются.

## 14. Демонстрационный набор форматов

Mock-данные должны покрывать разные типы файлов и контейнеров, чтобы в прототипе проверялись все основные сценарии:

* `.msg`
* `.zip`
* `.rar`
* `.7z`
* `.tar`
* `.doc`
* `.docx`
* `.xls`
* `.xlsx`
* `.pdf`
* `.jpg`
* `.jpeg`
* `.png`
* `.txt`

Верхнеуровневых элементов должно быть не меньше семи. Вложенность допускается до пятого уровня, но только через контейнерные форматы.
