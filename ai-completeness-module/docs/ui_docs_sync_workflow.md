# UI + Docs: маршрут синхронизации прототипа и документации

Этот документ задает рабочее правило для изменений внутри пакета `ai-completeness-module`: любое изменение UI должно сопровождаться проверкой связанной документации. Указанные ниже пути относятся к корню этого пакета, а не к корню принимающего приложения.

## 1. Основное правило

Если меняется интерфейс, поведение, структура данных, пользовательский сценарий, статус, селектор или состав компонента, нужно:

1. Определить затронутый компонент.
2. Открыть `docs/component_registry.json`.
3. Найти компонент в блоке `components`.
4. Проверить документы из `primary_docs`.
5. Проверить документы из `conditional_docs`, если условие `review_when` относится к текущей правке.
6. Обновить документацию там, где фактический UI или данные изменились.
7. В финальном ответе указать, какие документы были обновлены, либо явно сказать, что документация проверена и изменений не потребовала.

Для быстрой проверки маршрута можно использовать команду:

```bash
node scripts/docs-sync-check.js <changed-file> [changed-file...]
```

Например:

```bash
node scripts/docs-sync-check.js src/components/FileTree/FileTree.js src/components/FileTree/FileTree.css
```

Команды выше выполняются из корня пакета. Скрипт также можно запустить из принимающего проекта, указав путь к самому скрипту; аргументы файлов по-прежнему задаются относительно пакета. Реестр находится относительно скрипта, независимо от текущего каталога. Команда только выводит маршрут проверки: она не подтверждает актуальность текста и не заменяет просмотр связанных документов или сценарную приёмку. Новые зависимости для её запуска не нужны.

## 2. Что считается изменением, требующим проверки docs

Проверка документации обязательна, если меняется хотя бы один из пунктов:

* состав UI-элементов;
* расположение элементов;
* названия кнопок, алертов, вкладок, статусов или пунктов меню;
* логика появления/скрытия элементов;
* состояние обработки или цветовая индикация;
* структура строки, карточки, панели или виджета;
* DOM-селекторы, ID или классы, которые упомянуты в документации;
* mock-данные, JSON-контракт или атрибуты сущностей;
* пользовательский путь;
* связь между компонентами.

## 3. Когда документацию можно не менять

Документацию можно оставить без изменений, если правка не влияет на описанную спецификацию:

* исправлен внутренний комментарий в коде;
* исправлена опечатка, не влияющая на UI;
* изменен неописанный технический фрагмент;
* выполнен мелкий refactoring без изменения поведения, селекторов и данных.

Даже в этих случаях нужно кратко указать, что связанные документы проверены и изменений не потребовали.

## 4. Как пользоваться registry

Пример: изменено дерево документов.

1. Затронутый компонент: `FileTree`.
2. В `docs/component_registry.json` открывается `components.FileTree`.
3. Обязательная документация:
   * `src/components/FileTree/file_tree_and_pipelines.md`
4. Условная документация:
   * `docs/design_system_statuses.md` — если менялись статусы, цвета или индикаторы;
   * `docs/project_structure_map.md` — если менялся состав файлов;
   * `docs/README.md` — если менялось назначение компонента;
   * `src/components/MetadataPanel/metadata_panel.md` — если изменилась связь дерева с правой панелью.

## 5. Уровни обновления документации

Обновление может быть трех типов:

1. **Компонентное:** правится markdown внутри `src/components/<Component>/`.
2. **Глобальное:** правится документация в `docs/`, если изменение затрагивает общие правила проекта.
3. **Связующее:** правится документация соседнего компонента, если изменился контракт между компонентами.

## 6. Обязательство для Codex

При выполнении UI-задач Codex должен считать этот workflow частью задачи, даже если пользователь отдельно не просит обновлять документацию.

Для пользователя это должно выглядеть как единая работа:

```text
Изменение UI -> проверка registry -> обновление связанных docs -> финальный отчет
```

Нельзя оставлять документацию заведомо устаревшей после изменения прототипа.

На этот маршрут ссылается [AGENTS.md пакета](../AGENTS.md), чтобы правило `UI + Docs` действовало как локальная инструкция. Правила интеграции с принимающим приложением определяются документацией этого приложения.
